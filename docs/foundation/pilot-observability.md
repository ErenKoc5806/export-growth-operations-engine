# FND-009 — Operational diagnostics

`PilotLogger` appends JSONL to `operations.jsonl` in the private `EGO_DATA_DIR`. Each record has UTC time, a fixed event/outcome, canonical correlation UUID, optional bounded error category and nonnegative duration in milliseconds. There are no free-form message, contact, quote, PO, document or credential fields. The file must be owner-only (`0600`) under a private (`0700`) directory. The synthetic CLI emits one success or validation-failure event when `EGO_DATA_DIR` is configured; it does not record the input or exception text. The event list can grow only through reviewed enum additions at real workflow boundaries.

This stream explains whether a local operation ran and provides a correlation ID to follow retries. It is **not** the business record: SQLite `audit_event`, `access_decision`, approvals and action attempts are authoritative for decisions and external actions. File logging occurs outside those transactions and can fail independently. A failed log write does not imply a business rollback. Future external adapters must create an attempt ID and reconcile unknown provider outcomes before retrying; an operational success line is not proof of email delivery or ERP acceptance.

During pilot operation, check recent failures and their correlation IDs, compare them with the database's access/audit records, and investigate before retrying. Rotate the local log to another owner-only file when it grows, keep rotated copies under the same private storage controls, and set an operator-approved retention period before collecting real case data. Do not attach raw logs to public issues. No metrics server, alerting service or remote log collector is configured yet.
